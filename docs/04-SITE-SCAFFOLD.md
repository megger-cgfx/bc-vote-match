# BCVM M4 — Next.js static scaffold

_Card `<task-id>` · written 2026-10-01 by flower · the M4 build notes_

M4 is the **scaffold**: a static site that builds green against `docs/SCHEMA.md` and
can render the dataset the moment M2/M3 land. It is *not* the step that wires the
real codings in (that is M5, `<task-id>` / `docs/04-INTEGRATION.md`) and *not* the
public launch (that is `<task-id>` / `docs/05-LAUNCH.md`).

This file is referenced by `.gitignore` (the `attic/` entry) and by
`src/lib/scoring.ts` (the open spec issue). It documents what the scaffold is, what
was verified by execution, the defects found and fixed, and the two things that
still need a human.

## What exists

- **Build config.** `package.json`, `next.config.mjs` (`output: "export"` — fully
  static, no server runtime, no DB, no PII), `postcss.config.mjs`, `tsconfig.json`,
  Tailwind v4 via `src/app/globals.css`. Pinned: next 15.5.27, react 19.3.0,
  tailwind 4.3.3, typescript 5.9.3.
- **`src/lib/`**
  - `schema.ts` — 1:1 TypeScript mirror of `docs/SCHEMA.md`. Change both together.
  - `site.ts` — site-level copy + metadata, and `pageOg()` so every page repeats the
    share card (Next replaces the whole `openGraph` object per page).
  - `scoring.ts` — the v1 rules from the schema, plus `MIN_PAIRS = 5`. See the open
    spec issue below.
  - `data.ts` — build-time `fs` loader. Prefers the real `data/` files and falls back
    to `src/fixtures/*.sample.json`; sets `isFixture` and a loud `fixtureNote` whenever
    a fallback fires, so placeholder data cannot ship silently. `BCVM_FORCE_FIXTURES=1`
    forces the sample set for demoing the UI.
  - `store.ts` — localStorage progress + `?a=` share-link encoding. No accounts, no
    network, no cookies.
- **Routes.** `/`, `/questions`, `/results`, `/parties`, `/methodology`,
  `/coding-table`, `/about`, `/riding`, `not-found`, plus `robots.ts`, `sitemap.ts`,
  `icon.svg`.
- **Components.** `Likert`, `QuestionFlow`, `ResultsView`, `Compass`, `AlignmentBars`,
  `ShareCard`, `FixtureBanner`, `SiteHeader`, `SiteFooter`, `RidingLookup`.
- **Fixtures.** `src/fixtures/` — 18 sample questions, 5 parties, placeholder codings,
  10 fake sources, generated by `scripts/make-sample-codings.py`.
- **Share card.** `public/og.png` — a real 1200×630 card rendered by
  `scripts/make-og.py` (Pillow), referenced as `og:image` on every page.
- **Tests.** `scripts/smoke-test.mjs` — executable checks on `scoring.ts` and the
  exported `out/` (no browser needed).

## Defects found and fixed

1. **Cross-party coding contamination (real bug).** `alignmentForParty` indexed all
   parties' codings by `question_id` alone, so a party with `null` on a question
   inherited another party's code and the result was silently wrong. Fixed by filtering
   to `c.party_slug === partySlug` before indexing. Now covered by an explicit smoke
   check ("parties are scored against their own codings, never a neighbour's").
2. **M3 audit sidecars loaded as coding rows.** `data/codings/_*.json` (citation audit,
   conflicts, verification) were being read as codes. `data.ts` now skips `.`- and
   `_`-prefixed files and filters malformed rows.
3. **Compass label clipping.** A `+2/+2` voter's label ran off the SVG. Fixed by
   flipping labels near the right edge and adding a halo.

## Open spec issue — the alignment denominator (needs Martin)

`docs/SCHEMA.md` defines alignment as `1 − (Σ|user−party| / (2·n))`. Both sides live on
the −2…+2 scale, so one maximally-opposed question contributes a distance of 4 and the
formula can return **−100%** where a similarity score should bottom out at 0%. The
denominator should be `4·n` (the full span of the distance). This is a methodology
change, and methodology sits behind a human gate, so this build implements the formula
**as written** and clamps the *displayed* value to 0–100 (`percent`), keeping the
unclamped value in `rawPercent` so the discrepancy is visible rather than smoothed over.
Do not change it without a decision. Tracked on the board as a methodology-gate card.

## M4 → M5 boundary

Everything above runs on the **fixture** dataset or whatever real rows already exist in
`data/`, whichever `data.ts` finds. Swapping fully onto the real, sourced dataset is
M5's job: fail `next build` when `isFixture` is true, and render the published coding
table from real codings. M4 deliberately does not add that build-time assertion, because
until M2 freezes the questions and M3 finishes coding, a fixture build is the *correct*
state for development and the assertion would block every `next build`.
